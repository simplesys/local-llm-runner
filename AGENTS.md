# Правила для ИИ-агентов

`CLAUDE.md` — ссылка на этот файл, правки вносятся только сюда.

## Кто ты

- **Локальная модель** (Qwen 3.8 27B, Ornith 1.5 и другие модели, запущенные через `locallm`) — дальше этот файл не читай. Прочитай `docs/local_llm_agents_en.md` и работай только по нему: там весь нужный тебе минимум.
- **Облачная модель** — работай по этому файлу.

## Документация

1. Прежде чем браться за задачу, изучи три документа в папке `docs/` — и только их; подкаталог `archives/` не читай, см. п. 6. Пункт относится к облачным моделям; локальные модели этот шаг пропускают — они не читают ни эти три документа, ни `AGENTS.md`, их минимум собран в `docs/local_llm_agents_en.md`:
   - `project_description.md` — это текущее описание проекта, что он делает: актуальные требования;
   - `technical_description.md` — как он устроен: пакеты, зависимости, команды, технические решения;
   - `code_style.md` — как писать код.
2. Код должен соответствовать всем трём документам. Если документ расходится с задачей или с кодом — сообщи разработчику, а не выбирай молча.
3. Документация обновляется в том же изменении, что и код:
   - изменилось поведение для пользователя или статус требования → `project_description.md`;
   - появилась библиотека, технология, пакет, команда или техническое решение → `technical_description.md`;
   - появилось правило кода или линтера → `code_style.md`;
   - принято решение — запись с датой и причиной: продуктовое → `archives/changelog_product.md`, техническое → `archives/changelog_technical.md`.
4. Документы описывают фактическое состояние; планы помечаются явно.
5. В актуальных документах — только действующее состояние проекта. Изменённые и отменённые требования, решения и разделы в них не остаются ни в каком виде, в том числе с пометками «устарело» или «отменено»: их текст удаляется из документа и переносится в архив по правилам из шапки соответствующего журнала. Удалять устаревшее молча, без записи в журнал, нельзя.
6. `docs/archives/` — архив: журналы решений и перенесённые туда устаревшие части документов. В работе он **не используется**: контекст берётся только из актуальной документации. Открывать архивные файлы можно в двух случаях:
   - чтобы добавить новую запись — она всегда идёт сверху таблицы;
   - если разработчик прямо попросил изучить историю.

   В остальных случаях читать архив и добавлять его содержимое в запрос запрещено: это лишний объём контекста.

## Как работать агенту

### Сначала думай, потом пиши

Не строй догадок и не скрывай, что чего-то не понял.

- До начала работы озвучь, как ты понял задачу. Есть сомнения — спроси разработчика.
- Видишь путь проще — предложи его; считаешь подход неудачным — возрази с аргументами.
- Если задачу можно понять по-разному, перечисли варианты и оставь выбор разработчику.
- Что-то неясно — остановись и уточни, прежде чем продолжать.
- Формулируй так, чтобы тебя нельзя было понять двояко.

### Трогай только нужное

В изменение попадает лишь то, без чего задачу не решить.

- Не «улучшай» попутно соседний код, комментарии и форматирование.
- Не переписывай то, что работает.
- Следуй принятому в проекте стилю, даже если сам сделал бы иначе.
- Импорты, переменные и функции, которые стали лишними из-за твоих правок, удаляй. О мёртвом коде, существовавем до тебя, обязательно сообщай и спрашивай что делать с ним у разработчика.

Критерий: каждую изменённую строку можно объяснить планом.

### Не усложняй (следуй принципу KISS Keep it simple, stupid)

Пиши минимум кода, которого достаточно для решения.

- Никаких возможностей сверх запрошенного, никакой «гибкости» и настроек, о которых не просили.
- Не обрабатывай ошибки для сценариев, которые не могут произойти.
- Интерфейсы, generics, новые пакеты и абстракции — только когда без них не обойтись.
- Если решение получилось в разы объёмнее необходимого — перепиши короче.

Критерий: опытный разработчик не назвал бы это переусложнением.

### Добивайся проверяемого результата

Сначала определи, по какому признаку задача считается решённой, и работай, пока он не подтвердится.

- "Добавить функционал" → написаны тесты на некорректный и корректный сценарии, и они проходят.
- "Исправить ошибку" → есть тест, воспроизводящий прежнюю ошибку, и теперь он проходит.
- "Отрефакторить" → тесты зелёные и до, и после изменений.

Сложную задачу разбей на короткий план «шаг → чем проверить». Чёткие критерии позволяют двигаться без постоянных уточнений, размытые — нет.

### Задачи для локальных моделей

Когда разработчик просит подготовить задачу для локальной модели:

- текст задачи — на английском языке;
- в задаче нет развилок: никаких «на выбор исполнителя», вариантов решения и мест, которые можно понять двояко;
- каждый файл, идентификатор, сигнатура и команда проверки названы явно; сказано, что считается выполненным и чем это проверяется;
- если шаг использует внешний модуль, в задаче обязателен раздел «Dependency (Dependencies) to add in this step» с точным import path, точной версией и командой `go get <path>@<version>`: локальной модели разрешены только стандартная библиотека, уже подключённые модули и модули из этого раздела, поэтому без него она либо остановится с вопросом, либо напишет свою реализацию на стандартной библиотеке;
- если развилку или неоднозначность нельзя убрать самостоятельно — остановись и задай вопрос разработчику **на русском языке**, не выбирая вариант молча.

## Go

- Задача не выполнена, пока не зелёный `make check`: форматирование, линтеры, тесты с `-race`, `go mod tidy`.
- Пиши идиоматичный Go по `docs/code_style.md`. Линтеры не глушить: `//nolint` — только точечно и с объяснением и комментарием в ккоде, `.golangci.yml` не ослабляется.
- Новый код покрывается тестами; тесты не ходят в сеть и не требуют LM Studio.
- Сначала стандартная библиотека. Новая зависимость — только с обоснованием и записью в `technical_description.md`.
- Не меняй версию Go в `go.mod` и мажорные версии зависимостей без запроса.

## Правки разработчика

1. Если после правок разработчика тесты упали, исправляй тесты, а не его код. Падающий тест — не повод откатывать изменения.
2. Код разработчика нельзя удалять, менять или ослаблять без его явного согласия.
3. Если задача касается кода, который разработчик уже правил, добавляй поверх только строго необходимое.

## Запреты

- Не делай `git commit`, `git push`, не создавай ветки и не переписывай историю без просьбы.
- Не читай и не коммить `.env` и другие секреты.
- Не добавляй в сообщения коммитов, описания pull request и любые другие файлы проекта строки авторства ИИ — `Co-Authored-By`, `Claude-Session`, `Generated with` и подобные. Это касается и текстов, которые ты только предлагаешь разработчику.
