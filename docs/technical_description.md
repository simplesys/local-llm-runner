## 1. Стек

| Компонент | Выбор |
|---|---|
| Язык | Go (версия — в `go.mod`, сейчас 1.27) |
| Модуль | `github.com/simplesys/local-llm-runner` |
| Внешние зависимости | нет — только стандартная библиотека |
| Бэкенд LLM | LM Studio, OpenAI-совместимый REST API (`http://localhost:1234/v1`) |
| Разбор флагов | стандартный пакет `flag` |
| Форматирование | gofumpt + goimports (через golangci-lint) |
| Линтеры | golangci-lint v2, конфигурация — `.golangci.yml` |
| Платформы | macOS arm64 — основная, Linux — желательно |

## 2. Структура репозитория

```
cmd/local-llm-runner/   точка входа
internal/app/           composition root: конфигурация и сборка зависимостей
internal/config/         конфигурация: флаги > env > значения по умолчанию
internal/llm/           клиент OpenAI-совместимого API                  [заготовка]
internal/agent/         агентский цикл: диалог, вызовы инструментов     [заготовка]
internal/tools/         инструменты модели: файлы, поиск, shell         [заготовка]
internal/metrics/       метрики сессии                                  [заготовка]
internal/ui/            терминальный интерфейс                          [заготовка]
docs/                   документация
```

Заготовка — пакет, в котором есть только `doc.go` с описанием ответственности и ссылками на требования (FR).

## 3. Зависимости между пакетами

Разрешённые импорты; обратные направления запрещены:

- `cmd` → `app`
- `app` → любые пакеты `internal/`
- `ui` → `agent`, `metrics`
- `agent` → `llm`, `tools`, `metrics`
- `config`, `llm`, `tools`, `metrics` — листовые, другие пакеты `internal/` не импортируют.

`agent` не знает о терминале: он публикует события, а `ui` их отображает.

## 4. Точка входа и жизненный цикл

1. `main` создаёт корневой контекст через `signal.NotifyContext` (SIGINT, SIGTERM) и вызывает `app.Run`.
2. `app.Run(ctx, app.Options)` получает всё, что связано с процессом, — аргументы, `Getenv`, `Stdout`, `Stderr`, версию — через `Options`. Поэтому `Run` тестируется целиком, без глобального состояния.
3. Ошибку `main` превращает в код выхода: `0` — успех, `1` — ошибка выполнения, `2` — ошибка использования (`errors.Is(err, app.ErrUsage)`).

Версия определяется так: `-ldflags "-X main.version=..."` (`make build` подставляет `git describe`) → версия модуля из `debug.ReadBuildInfo` → `dev`.

## 5. Конфигурация

`config.Load(args, getenv)` применяет значения по умолчанию, затем переменные окружения, затем флаги и проверяет результат. Флаги разбираются через `flag.FlagSet` в режиме `ContinueOnError`, собственный вывод пакета `flag` отключён: ошибки возвращаются вызывающему, справку печатает `app`. Запрос справки возвращает ошибку, совместимую с `flag.ErrHelp`.

Список параметров — в `project_description.md`, раздел 7.

## 6. Взаимодействие с LM Studio

Планируемые эндпоинты (проверить на реальном сервере при реализации):

| Назначение | Запрос |
|---|---|
| Список моделей (FR-6) | `GET /v1/models`; отметка «загружена», вероятно, потребует нативного API LM Studio (`/api/v0/models`) |
| Диалог и инструменты (FR-7, FR-8) | `POST /v1/chat/completions` с `stream: true` (SSE) и `tools` |
| Токены (FR-12) | поле `usage`; в потоковом режиме — `stream_options.include_usage` |

- Ключ API не передаётся.
- `*http.Client` создаётся в `app`. `Client.Timeout` не задаётся, чтобы не обрывать долгую генерацию; время ограничивается контекстом и таймаутами `http.Transport`.

## 7. Исполнение действий модели

- Файловые инструменты открывают рабочую директорию через `os.OpenRoot` и работают только через `os.Root`: выйти за её пределы через `..` или симлинки нельзя.
- Shell-команды запускаются через `exec.CommandContext` с таймаутом, рабочей директорией workspace, ограничением объёма вывода и только после подтверждения (FR-9).
- Результат для пользователя идёт в stdout; диагностика, прогресс и метрики — в stderr.

## 8. Сборка и проверки

| Команда | Назначение |
|---|---|
| `make check` | `tidy-check` + `lint` + `test` — должно быть зелёным перед завершением изменения |
| `make test` | `go test -race -count=1 ./...` |
| `make lint` | `golangci-lint run` (включая `go vet` и проверку форматирования) |
| `make fmt` | `golangci-lint fmt` |
| `make build` | бинарник `bin/local-llm-runner` |
| `make run ARGS="..."` | запуск из исходников |
| `make cover` | покрытие тестами |
| `make vuln` | `govulncheck` |

Для разработки нужны Go версии из `go.mod` и golangci-lint v2 (`brew install golangci-lint`). CI пока не настроен.

## 9. Тестирование

- Unit-тесты — стандартный `testing`, запуск с `-race`. Сервер LLM подменяется `httptest`, записанные ответы API лежат в `testdata/`. Сеть и LM Studio не нужны.
- Интеграционные тесты с реальной моделью — под build-тегом `integration`: `go test -tags=integration ./...`. Требуют запущенного LM Studio.

## 10. Окружение разработки

- LM Studio: сервер запускается командой `lms server start`; `lms ps` показывает загруженные модели, `lms ls` — скачанные.
- Скиллы агентов лежат в `.agents/skills/`. `.claude/skills` — симлинк на этот каталог, по аналогии с `CLAUDE.md` → `AGENTS.md`: набор скиллов общий и не привязан к конкретному клиенту. Новые скиллы создаются только в `.agents/skills/`.
- Скилл `commit-message` (`.agents/skills/commit-message/SKILL.md`): по сообщениям «коммит», «сообщение для коммита», «commit», «commit message» составляет текст коммита в формате Conventional Commits по текущему diff и печатает его в чат. Сам ничего не коммитит.
- Bash-прототип лежит в родительском каталоге рабочей копии автора (`../llm-agent.sh`, `../llm-codex.sh`, `../agent-common.sh`, `../run-under-pty.py`, `../list-models.sh`) и в репозиторий не входит. Это только эталон поведения, его не изменяют. Описание — в `project_description.md`, раздел 4.
