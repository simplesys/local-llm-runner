## 2. Структура репозитория

```
cmd/locallm/   main: контекст, сигналы, вызов app.Run, код выхода
internal/app/           composition root: сборка зависимостей, режимы запуска
internal/config/        конфигурация и настройки: флаги > env > файл > дефолты
internal/llm/           клиент OpenAI-совместимого API: SSE, tool calls, usage
internal/lmstudio/      модели LM Studio: список, загрузка и выгрузка, лок
internal/agent/         агентский цикл: диалог, вызовы инструментов, события
internal/tools/         инструменты модели: файлы, поиск, shell
internal/sandbox/       уровни песочницы для shell-команд
internal/session/       история сессий: запись, индекс, ретенция
internal/metrics/       метрики сессии: сбор, печать, файл
internal/ui/            терминальный интерфейс и слэш-команды
docs/                   документация
```

Запланированные пакеты (каталогов пока нет): `internal/mcp` (клиент и серверный режим), `internal/skills`, `internal/workflow`.

## 3. Зависимости

Внешних модулей в `go.mod` нет: весь текущий код — на стандартной библиотеке. Правило на будущее: зависимость добавляется в том же изменении, что и код, который её использует, с обоснованием здесь и записью в журнале технических решений. Ожидаемые зависимости запланированных задач: Bubble Tea, Lipgloss, Bubbles и Glamour (полноэкранный интерфейс), официальный Go SDK MCP, `go-landlock` (песочница Linux), `go-cmp` (сравнение структур в тестах).

Важно: модули Charm второй мажорной версии живут на `charm.land/*`, а не на `github.com/charmbracelet/*` — иначе `go mod tidy` падает с «module declares its path as».

## 4. Зависимости между пакетами

Разрешённые импорты; обратные направления запрещены:

- `cmd` → `app`
- `app` → любые пакеты `internal/`
- `ui` → `agent`
- `agent` → `llm`, `tools`
- `tools` → `sandbox`
- `config`, `llm`, `lmstudio`, `sandbox`, `session`, `metrics` — листовые, другие пакеты `internal/` не импортируют

`agent` не знает о терминале и о хранилищах: он публикует события, которые потребляют `ui` (отображение), `session` (запись) и `metrics` (подсчёт). Интерфейсы объявляются в пакете-потребителе: `agent` описывает, что ему нужно от клиента LLM и от реестра инструментов; `tools` — что ему нужно от песочницы; `lmstudio.Switcher` — что ему нужно от API и от CLI.

## 5. Точка входа и жизненный цикл

1. `main` создаёт корневой контекст через `signal.NotifyContext` (только SIGTERM) и вызывает `app.Run`. SIGINT обрабатывает `app`: первое нажатие прерывает текущую задачу, второе в течение двух секунд завершает программу, поэтому процесс не должен умирать от первого сигнала.
2. `app.Run(ctx, app.Options)` получает всё, что связано с процессом, — аргументы, `Getenv`, `Stdin`, `Stdout`, `Stderr`, версию, признак терминала — через `Options`, поэтому тестируется целиком.
3. Порядок сборки сессии: настройки → конфигурация → рабочая директория → HTTP-клиент → список моделей → выбор модели → переключение модели (лок + `lms`) → песочница → инструменты → метрики и история → клиент LLM → агент → режим работы → метрики и закрытие ресурсов.
4. Ошибку `main` превращает в код выхода через sentinel-ошибки `app`: `ErrUsage` → 2, `ErrLimit` → 3, `ErrBackend` → 4, остальное → 1.

Версия определяется так: `-ldflags "-X main.version=..."` → версия модуля из `debug.ReadBuildInfo` → `dev`.

## 6. Конфигурация и состояние на диске

`config.Load(args, getenv, settings)` применяет значения по умолчанию, затем файл настроек, затем переменные окружения, затем флаги, и проверяет результат. Флаги разбираются через `flag.FlagSet` в режиме `ContinueOnError`, вывод пакета `flag` отключён: ошибки возвращаются вызывающему, справку печатает `app`.

Каталог состояния — `os.UserConfigDir()/locallm`, переопределяется переменной `LOCAL_LLM_CONFIG_DIR` (нужно и пользователям, и тестам, чтобы не трогать настоящий каталог):

```
settings.json          настройки
sessions/index.json    индекс истории
sessions/<id>.jsonl    записи сессии
metrics/<id>.json      метрики сессии
lms.lock               лок переключения моделей
```

Файлы состояния пишутся атомарно (временный файл + `os.Rename`). Повреждённый `settings.json` даёт предупреждение и значения по умолчанию; повреждённый или отсутствующий индекс сессий перестраивается сканом каталога; обрыв записи в JSONL теряет только последнюю строку.

Идентификатор сессии — `20060102-150405-<6 hex>`: сортируется хронологически и проверяется регулярным выражением перед превращением в имя файла.

## 7. Взаимодействие с LM Studio

Проверено на реальном сервере, перепроверять не нужно:

| Что | Факт |
|---|---|
| Список моделей | `GET /api/v0/models` отдаёт `id`, `type`, `state`, `capabilities` (инструменты — `tool_use`), `max_context_length`, `loaded_context_length`, `quantization` |
| Диалог и инструменты | `POST /v1/chat/completions` с `stream: true`, `stream_options.include_usage` и `tools` |
| Токены | только поле `usage`; в потоке приходит последним чанком |
| Загрузка и выгрузка | REST-эндпоинтов нет: `POST /api/v0/models/load`, `/api/v0/load`, `/api/v0/unload`, `DELETE /api/v0/models/<id>` отвечают `Unexpected endpoint or method` |
| Токенизация | эндпоинта нет; занятость контекста можно только оценивать (≈4 символа на токен) с коррекцией по фактическому `usage.prompt_tokens` |
| JIT-загрузка | для переключения не годится: зависит от настроек сервера, не выгружает вручную загруженные модели и не даёт прогресса |
| CLI `lms` | `lms unload -a` выгружает всё; `lms load <id> -y [--context-length N]` загружает; `lms ps --json` отвечает за ~0.2 с |
| Внутренний API приложения | WebSocket на порту из `~/.lmstudio/.internal/http-server.json` существует, но не документирован — не используем |

Клиент LLM (`internal/llm`) — свой, на `net/http`: LM Studio расширяет формат OpenAI (`reasoning_content`), а SSE-парсер занимает около сотни строк. `*http.Client` создаётся в `app`; `Client.Timeout` не задаётся, чтобы не обрывать долгую генерацию (`NewClient` это проверяет), время ограничивается контекстом и таймаутами `http.Transport` (`DialContext` 5 с, `ResponseHeaderTimeout` 60 с). `bufio.Scanner` для SSE — с буфером до 1 МБ: одна строка `data:` может содержать весь список аргументов вызова. Поле `reasoning_content` в запросах не отправляется.

Поиск `lms` (`internal/lmstudio`): `PATH`, затем `$LMSTUDIO_HOME` и домашний каталог — `~/.lmstudio/bin/lms`, `~/.cache/lm-studio/bin/lms`, на Windows `%USERPROFILE%\.lmstudio\bin\lms.exe` и `%USERPROFILE%\AppData\Local\LM Studio\lms.exe` (пути Windows на реальной машине не проверены). Переключение: выгрузить всё → загрузить нужную → дождаться состояния `loaded` по API. Лок `lms.lock` содержит PID и время; лок снимается, если процесс-владелец мёртв (на Windows — только по возрасту записи) или запись старше 10 минут.

## 8. Исполнение действий модели

- Файловые инструменты открывают рабочую директорию через `os.OpenRoot` и работают только через `os.Root`: выйти за её пределы через `..`, абсолютный путь или симлинк нельзя. Самодельных проверок пути нет.
- Изменяющая запись идёт через временный файл в том же каталоге и `Root.Rename`, поэтому прерванная запись не оставляет полуфайла. Права файлов `0o644`, каталогов `0o755` (линтер gosec на этих местах отключён точечно, с ссылкой на правило стиля).
- Shell-команды: строка передаётся аргументом интерпретатору (`sh -c` на macOS и Linux, `powershell -NoProfile -Command` на Windows), список аргументов формирует программа. Контекст с таймаутом, stdin закрыт, stdout и stderr собираются отдельно и обрезаются, окружение дополняется `LOCALLM=1`.
- Ненулевой код выхода и таймаут — не ошибка Go, а нормальный результат инструмента: модель должна увидеть код и вывод.
- Песочница (`internal/sandbox`) готовит `*exec.Cmd` и сообщает достигнутый уровень; запуском занимается `tools`. На macOS команда оборачивается в `sandbox-exec` с профилем: чтение везде (компиляторам нужны системные библиотеки), запись только в рабочую директорию, каталоги кэшей и временный каталог, сеть запрещена. Пути в профиле разворачиваются через `filepath.EvalSymlinks`, потому что Seatbelt сопоставляет реальные пути (на macOS `/var` — симлинк на `/private/var`). Реализации по платформам разделены build-тегами, поэтому кросс-сборка проходит.
- Результат для пользователя идёт в stdout; диагностика, прогресс, подтверждения и метрики — в stderr. В интерактивном режиме ввод читает одна горутина-владелец, и она ничего не печатает: два писателя в один поток дали бы перемешанный вывод и гонку.

## 9. Сборка и проверки

| Команда | Назначение |
|---|---|
| `make check` | `tidy-check` + `lint` + `test` — должно быть зелёным перед завершением изменения |
| `make test` | `go test -race -count=1 ./...` |
| `make test-integration` | тесты, требующие запущенного LM Studio (`-tags=integration`) |
| `make lint` | `golangci-lint run` (включая `go vet` и проверку форматирования) |
| `make fmt` | `golangci-lint fmt` |
| `make build` | бинарник `bin/locallm` |
| `make crossbuild` | проверка кросс-сборки под linux/amd64, windows/amd64, darwin/arm64 с `CGO_ENABLED=0` |
| `make run ARGS="..."` | запуск из исходников |
| `make cover` | покрытие тестами |
| `make vuln` | `govulncheck` |

Для разработки нужны Go версии из `go.mod` и golangci-lint v2 (`brew install golangci-lint`). CI пока не настроен.

## 10. Тестирование

- Unit-тесты — стандартный `testing`, запуск с `-race`. Сервер LLM подменяется `httptest`, записанные SSE-потоки лежат в `testdata/`, CLI `lms` — исполняемым скриптом-заглушкой в `t.TempDir()`. Сеть и LM Studio не нужны.
- Тесты, которые пишут на диск, работают только в `t.TempDir()`; каталог настроек пользователя подменяется через `LOCAL_LLM_CONFIG_DIR`.
- Большой ожидаемый вывод (метрики, системный промпт, профиль песочницы) сравнивается с golden-файлами `testdata/*.golden`, обновляемыми флагом `-update`.
- Парсер SSE покрыт fuzz-тестом (`go test -run=Fuzz -fuzz=FuzzDecodeStream ./internal/llm`); в `make check` фаззинг не входит.
- Безопасность проверяется тестами явно: выход за рабочую директорию через `..`, абсолютный путь и симлинк; отклонение git-команд; запись за пределы песочницы на macOS.
- Тесты, требующие POSIX-шелла или `sandbox-exec`, пропускаются через `t.Skip` там, где их выполнить нельзя.

## 11. Окружение разработки

- LM Studio: сервер запускается командой `lms server start`; `lms ps` показывает загруженные модели, `lms ls` — скачанные.
- Скиллы агентов лежат в `.agents/skills/`. `.claude/skills` — симлинк на этот каталог, по аналогии с `CLAUDE.md` → `AGENTS.md`: набор скиллов общий и не привязан к конкретному клиенту. Новые скиллы создаются только в `.agents/skills/`.
- Скилл `commit-message` (`.agents/skills/commit-message/SKILL.md`): по сообщениям «коммит», «сообщение для коммита», «commit», «commit message» составляет текст коммита в формате Conventional Commits по текущему diff и печатает его в чат. Сам ничего не коммитит.
- Bash-прототип лежит в родительском каталоге рабочей копии автора и в репозиторий не входит. Это историческая справка, его не изменяют; описание — в `project_description.md`, раздел 4.
