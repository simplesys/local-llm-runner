# Стиль кода Go

> Обязательные правила для всего кода в репозитории. Всё, что можно проверить автоматически, проверяет `make check`; остальное — на ревью.
>
> При конфликте источников приоритет такой: этот документ → [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) → [Google Go Style Guide](https://google.github.io/styleguide/go/) → [Effective Go](https://go.dev/doc/effective_go).

Дополнительные источники: [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md), [Go Proverbs](https://go-proverbs.github.io/), [Organizing a Go module](https://go.dev/doc/modules/layout).

## 0. Главные принципы

1. **Ясность важнее краткости и «умности».** Код читают намного чаще, чем пишут.
2. **Простота.** Решение без абстракции лучше решения с абстракцией, пока не появилась вторая реализация или реальная потребность.
3. **Идиоматичность.** Пишем так, как написана стандартная библиотека Go, а не как принято в Java, TypeScript, Python или PHP.
4. **Явность.** Никакой магии: нет глобального состояния, скрытых побочных эффектов в `init()`, рефлексии без необходимости.
5. **Стандартная библиотека в первую очередь.** Каждая внешняя зависимость — осознанное решение.

## 1. Инструменты

| Инструмент | Команда | Назначение |
|---|---|---|
| gofumpt + goimports | `make fmt` | форматирование (строже `gofmt`) и группировка импортов |
| golangci-lint v2 | `make lint` | `go vet`, staticcheck, errcheck, revive, gosec и др. — см. `.golangci.yml` |
| go test -race | `make test` | тесты с детектором гонок |
| go mod tidy | `make tidy-check` | `go.mod`/`go.sum` в чистом состоянии |
| govulncheck | `make vuln` | известные уязвимости в зависимостях |
| go fix | `go fix ./...` | модернизация кода под версию Go из `go.mod` |

- `make check` должен быть зелёным до того, как изменение считается завершённым.
- `//nolint` — только точечно, с именем линтера и причиной: `//nolint:gosec // path is confined by os.Root`. Ослаблять `.golangci.yml` ради прохождения проверки нельзя.
- Импорты — три группы: стандартная библиотека, внешние модули, пакеты этого модуля. `goimports` расставляет их сам.

## 2. Структура проекта

```
cmd/local-llm-runner/   main: контекст, сигналы, вызов app.Run, код выхода
internal/<package>/     весь код приложения, недоступен извне модуля
docs/                   документация
```

- `main` тонкий: создаёт корневой контекст, вызывает `app.Run`, превращает ошибку в код выхода. Бизнес-логики в `main` нет.
- Весь код — в `internal/`. Каталог `pkg/` не создаём: у проекта нет публичного API для сторонних модулей.
- Пакет = одна ответственность (`llm`, `tools`, `agent`), а не технический слой (`models`, `services`, `handlers`).
- Запрещённые имена пакетов: `util`, `utils`, `common`, `helpers`, `misc`, `base`, `types`, `shared`. Вспомогательный код живёт рядом с тем, кто его использует.
- Циклических зависимостей нет; разрешённое направление импортов описано в `docs/technical_description.md`. Нижние пакеты (`config`, `llm`, `tools`, `metrics`) не импортируют верхние (`agent`, `ui`, `app`).
- Тестовые данные — в `testdata/` рядом с тестом (Go tooling игнорирует этот каталог).
- Имена файлов — `snake_case.go`, тесты — `<file>_test.go`, описание пакета — `doc.go`.
- Ориентир по размеру: файл до ~500 строк, функция до ~60 строк. Превышение — повод разделить, а не жёсткий запрет.

## 3. Именование

- `MixedCaps` / `mixedCaps`, без подчёркиваний. Константы тоже: `DefaultModel`, а не `DEFAULT_MODEL`.
- Аббревиатуры пишутся в одном регистре: `baseURL`, `userID`, `ParseHTTP`, `llmClient`, `APIKey`. Не `BaseUrl`, `UserId`, `ParseHttp` (проверяет линтер `revive: var-naming`).
- Пакеты — короткие строчные существительные в одно слово: `config`, `llm`, `tools`. Не `llmClient`, `llm_client`.
- Без «заикания»: имя пакета — часть имени. `llm.Client`, а не `llm.LLMClient`; `config.Load`, а не `config.LoadConfig`.
- Короткие имена — только из общепринятого набора (`ctx`, `err`, `i`, `r`, `w`, `b`, `ok`) и только в коротких блоках. Остальные имена описательные, включая локальные переменные; для полей, пакетных и экспортируемых идентификаторов описательность обязательна.
- Получатель метода — 1–2 буквы от имени типа, одинаковый во всех методах: `func (c *Client)`. Никаких `this`/`self`.
- Геттеры без `Get`: `Model()`, а не `GetModel()`. Сеттер — `SetModel()`.
- Интерфейс с одним методом — суффикс `-er`: `Completer`, `Executor`, `Renderer`.
- Ошибки: переменные `ErrNotFound`, типы `NotFoundError` (проверяет линтер `errname`).
- Не переопределять встроенные идентификаторы: `len`, `new`, `error`, `min`, `max`, `any`, `clear`.

## 4. Оформление кода

**Happy path по левому краю.** Ошибку обрабатываем сразу и выходим; `else` после `return` не пишем.

```go
// ✅
f, err := os.Open(name)
if err != nil {
	return fmt.Errorf("open %s: %w", name, err)
}
defer f.Close()

// ❌
if f, err := os.Open(name); err == nil {
	// ... основная логика с вложенностью
} else {
	return err
}
```

- «Голый» `return` не используем. Именованные результаты — только для документации (несколько значений одного типа) или чтобы изменить результат в `defer`.
- Никаких `bool`-параметров, переключающих поведение (`render(msg, true)`) — отдельные функции или именованный тип.
- Литералы структур — с именами полей: `Config{Model: m}`, а не `Config{m, u}`.
- «Магические» числа и строки — в именованные константы.
- Связанные `const`/`var`/`type` группируются в блоки.
- `var x T` — для нулевого значения, `x := value` — при инициализации значением.
- Перечисления — отдельный тип с `iota`; нулевое значение означает «не задано» либо осмысленное значение по умолчанию. `switch` по перечислению — исчерпывающий (линтер `exhaustive`).

```go
type Mode int

const (
	ModeInteractive Mode = iota + 1
	ModeOneShot
)
```

- Восьмеричные литералы — с префиксом `0o`: `0o644`.

## 5. Пакеты, типы и API

- Экспортируем минимум. То, что можно не экспортировать, не экспортируем.
- **Принимай интерфейсы, возвращай конкретные типы.**
- Интерфейс объявляется **в пакете-потребителе** и содержит только те методы, которые потребителю нужны.

```go
// package agent: потребитель описывает, что ему нужно от клиента LLM.
type completer interface {
	Complete(ctx context.Context, req llm.Request) (llm.Response, error)
}
```

- Не создаём интерфейс «на будущее» или ради одного мока, если можно тестировать через `httptest` или `t.TempDir()`. Интерфейс появляется, когда есть вторая реализация или граница, которую нужно подменять.
- Когда реализация — это контракт, соответствие проверяется при компиляции: `var _ Tool = (*ReadFile)(nil)`.
- Нулевое значение типа по возможности полезно (как у `sync.Mutex`, `bytes.Buffer`). Иначе — конструктор `NewX(...)`, возвращающий готовый к работе объект.
- 1–3 обязательных параметра конструктора — обычные аргументы. Много необязательных — структура `Options` (по умолчанию) или functional options, если это действительно упрощает вызовы.
- Зависимости передаются явно через конструкторы. DI-фреймворки не используем.
- **Глобальное изменяемое состояние запрещено**: никаких пакетных `var client = ...`, никаких `init()` с вводом-выводом или побочными эффектами.
- Доступ к процессу (`os.Args`, `os.Getenv`, `os.Stdout`, `os.Exit`, текущее время) — только в `main` и `app`. Внутрь передаются значения, `io.Reader`/`io.Writer` и функции (`getenv func(string) string`, `now func() time.Time`).
- Получатели: если хотя бы один метод изменяет состояние, тип большой или содержит мьютекс — все методы с указателем. Не смешивать без причины.
- Срезы и map, полученные извне и сохраняемые внутри, копируются (`slices.Clone`, `maps.Clone`), если вызывающий может их изменить.
- Generics — только если они реально убирают дублирование (алгоритмы над коллекциями, контейнеры). Для полиморфизма поведения — интерфейсы.
- `any` вместо `interface{}`.

## 6. Ошибки

- Ошибка — значение, и она всегда проверяется. Игнорирование — только явно, `_ = f()`, с комментарием почему.
- При передаче наверх добавляется контекст через `%w`. Контекст — что делали, без слов «failed»/«error»:

```go
// ✅
return fmt.Errorf("load session %s: %w", id, err)

// ❌
return fmt.Errorf("failed to load session: error: %v", err)
```

- Текст ошибки — со строчной буквы, без точки в конце и переводов строк.
- Проверка — `errors.Is(err, ErrX)`; извлечение типа — `errors.AsType[*T](err)` (Go 1.26+) или `errors.As`. Нельзя сравнивать `err == ErrX` для потенциально обёрнутых ошибок и нельзя сравнивать `err.Error()` со строкой.
- Sentinel-ошибка (`var ErrNotFound = errors.New("not found")`) — когда вызывающему нужно различать случай. Тип ошибки — когда нужны данные. В остальных случаях — просто `fmt.Errorf`.
- Ошибка обрабатывается **один раз**: либо логируется, либо возвращается — не то и другое вместе.
- `panic` — только для ошибок программиста (нарушенный инвариант). Никогда для ожидаемых ситуаций: сеть, файлы, ввод пользователя или модели. Код вне `main` не вызывает `os.Exit` и `log.Fatal`.
- Несколько ошибок объединяются через `errors.Join`.
- Ошибки из `defer` для записываемых ресурсов не теряются:

```go
func writeFile(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() { err = errors.Join(err, f.Close()) }()

	_, err = f.Write(data)
	return err
}
```

## 7. Context

- `ctx context.Context` — первый параметр каждой функции, которая выполняет I/O, ждёт или работает долго.
- Context не хранится в полях структур.
- Корневой контекст создаётся в `main` через `signal.NotifyContext`, поэтому Ctrl+C отменяет всё дерево операций.
- Никогда не передаём `nil` вместо контекста; в тестах используем `t.Context()`.
- После `context.WithTimeout`/`WithCancel` — всегда `defer cancel()`.
- `context.WithValue` — только для метаданных уровня запроса, не для параметров и зависимостей.
- `context.WithoutCancel` — для операций, которые должны завершиться после отмены (например, сохранение истории сессии при выходе).

## 8. Конкурентность

- API синхронный по умолчанию. Конкурентность добавляет вызывающий, если она нужна.
- У каждой горутины есть владелец, который знает, как и когда она завершится. Горутина без механизма остановки — утечка.
- Группа горутин — `sync.WaitGroup.Go` (Go 1.25+); если нужны ошибки и отмена — `errgroup.Group`.

```go
var wg sync.WaitGroup
for _, f := range files {
	wg.Go(func() { index(ctx, f) })
}
wg.Wait()
```

- Каналы — для передачи владения данными и сигналов; мьютекс — для защиты состояния. Не используем каналы там, где достаточно мьютекса.
- Канал закрывает только отправитель. Буфер канала — 0 или 1; другой размер нужно обосновать.
- Мьютекс объявляется рядом с полями, которые защищает; не встраивается в экспортируемые структуры; структуры с мьютексом не копируются.
- Отправка и чтение в долгоживущей горутине — через `select` с `case <-ctx.Done()`.
- `time.Sleep` для синхронизации запрещён. Код, зависящий от времени, тестируется через `testing/synctest`.

## 9. Ввод-вывод, терминал, логирование

- **stdout** — только результат для пользователя: ответ модели, `--help`, `--version`. **stderr** — диагностика, прогресс, ошибки, метрики. Так вывод one-shot режима можно безопасно перенаправлять в файл или pipe.
- Логирование — `log/slog` со структурированными атрибутами; `*slog.Logger` передаётся через конструктор. `log.Printf` и `fmt.Println` для диагностики не используем.
- В интерактивном режиме логи не пишутся в терминал поверх интерфейса — только в файл, если логирование включено.
- Секреты и содержимое пользовательских файлов не логируются.
- Код работает с `io.Reader`/`io.Writer`, а не с `os.Stdout` и путями напрямую — это делает его тестируемым.

## 10. HTTP и клиент LLM

- Не используем `http.Get` и `http.DefaultClient`. `*http.Client` создаётся в `app` и передаётся в конструктор.
- Запросы создаются через `http.NewRequestWithContext` (линтер `noctx`).
- `resp.Body` закрывается всегда (линтер `bodyclose`). Статус проверяется до разбора тела; в ошибку попадают код статуса и усечённое тело ответа.
- Для потоковых (SSE) ответов нельзя задавать `http.Client.Timeout` — он оборвёт долгую генерацию. Ограничения времени — через context и таймауты `http.Transport` (`ResponseHeaderTimeout`, dial).
- `bufio.Scanner` для SSE — с увеличенным буфером (`scanner.Buffer`): строка ответа может превышать 64 КБ.
- JSON — структуры с тегами `json:"name,omitempty"`. Неизвестные поля не считаются ошибкой: LM Studio расширяет формат OpenAI.

## 11. Безопасность агента

Агент выполняет действия, предложенные моделью. **Вывод модели — недоверенный ввод.**

- Файловые инструменты работают только внутри рабочей директории через `os.Root` (`os.OpenRoot(workspace)`): это блокирует выход через `..` и симлинки. Самодельная проверка путей через `strings.HasPrefix` запрещена.
- Shell-команды: `exec.CommandContext` с таймаутом, рабочей директорией workspace и ограничением объёма захватываемого вывода; запуск только после подтверждения пользователя (FR-9).
- Аргументы других программ передаются списком `exec.Command(name, args...)`, без склейки строк и без `sh -c` — кроме явной shell-команды, подтверждённой пользователем.
- Данные, пришедшие от модели или пользователя, читаются с ограничением размера (`io.LimitReader`).
- Файлы создаются с правами `0o644`, каталоги — `0o755`. Файлы состояния пишутся атомарно: временный файл + `os.Rename`.

## 12. Комментарии и документация кода

- Идентификаторы, комментарии и godoc — **на английском**. Документация в `docs/` — на русском.
- У каждого экспортируемого идентификатора есть godoc-комментарий — полное предложение, начинающееся с имени: `// Load resolves the configuration ...`.
- У каждого пакета есть package comment (`// Package llm ...`) — в `doc.go` или главном файле пакета.
- Комментарий объясняет **почему**, а не **что**. Очевидный код не комментируется.
- `TODO` — с меткой и ссылкой на требование: `// TODO(agent-loop): stream tokens (FR-7)`.
- Закомментированный и мёртвый код не коммитится.
- Устаревший API помечается `// Deprecated: use X instead.`

## 13. Тестирование

- Стандартный пакет `testing`. Для сравнения сложных структур допустим `github.com/google/go-cmp/cmp`. Assertion-фреймворки (testify и подобные) не используем.
- Табличные тесты с `t.Run(tt.name, ...)`; имя случая описывает поведение: `"flags override environment"`.
- Сообщение об ошибке — сначала фактическое значение, потом ожидаемое:

```go
if got != tt.want {
	t.Errorf("Load(%q) = %+v, want %+v", tt.args, got, tt.want)
}
```

- `t.Fatal` — когда продолжать бессмысленно; `t.Error` — чтобы увидеть все расхождения сразу.
- Тестовые хелперы вызывают `t.Helper()` и принимают `t` первым аргументом.
- `t.Parallel()` — во всех тестах без общего состояния (несовместимо с `t.Setenv` и `t.Chdir`).
- Ресурсы: `t.TempDir()`, `t.Context()`, `t.Cleanup()`, `t.Setenv()`.
- Тесты публичного API — в пакете `foo_test` (чёрный ящик). Внутренний пакет `foo` — только для проверки неэкспортируемой логики.
- **Unit-тесты не требуют сети и запущенного LM Studio.** Сервер подменяется `httptest.NewServer`, записанные ответы API (включая SSE-потоки) лежат в `testdata/`.
- Интеграционные тесты с реальной моделью — под build-тегом `//go:build integration`, запуск: `go test -tags=integration ./...`.
- Большой ожидаемый вывод (метрики, рендеринг) — golden-файлы `testdata/*.golden`, обновляемые флагом `-update`.
- Парсеры (SSE, tool calls, JSON от модели) покрываются fuzz-тестами `func FuzzX(f *testing.F)`.
- Исправление бага сопровождается тестом, который воспроизводит баг.
- Бенчмарки пишутся через `for b.Loop() { ... }` (Go 1.24+).
- Покрытие — не самоцель, но бизнес-логика (`config`, `agent`, `tools`, `metrics`, парсеры в `llm`) покрыта тестами.

## 14. Зависимости

- Сначала стандартная библиотека и `golang.org/x/...`.
- Внешняя зависимость допустима, если она решает нетривиальную задачу (TUI, рендеринг markdown), активно поддерживается и имеет совместимую лицензию (MIT, BSD, Apache-2.0). Решение фиксируется в журнале технических решений `docs/archives/changelog_technical.md`.
- Не подключаем зависимость ради одной функции.
- `go.mod` и `go.sum` всегда в tidy-состоянии. Версия Go в `go.mod` повышается осознанно, отдельным изменением.

## 15. Производительность

- Порядок: корректность и ясность → измерение (бенчмарк, `pprof`) → оптимизация.
- Разумно и без измерений: `make([]T, 0, n)` при известном размере, `strings.Builder` для склейки в цикле, `strconv` вместо `fmt` для чисел.
- Файлы, указанные моделью или пользователем, не читаются целиком без ограничения размера.

## 16. Современный Go

Используем возможности версии Go из `go.mod`:

- `slices`, `maps`, `cmp`, `strings.Cut` вместо ручных циклов; встроенные `min`, `max`, `clear`.
- `for i := range n` для счётных циклов; итераторы `iter.Seq` и range-over-func для последовательностей.
- Переменная цикла уникальна для каждой итерации (Go 1.22+) — копия `v := v` не нужна.
- `errors.AsType`, `sync.WaitGroup.Go`, `testing/synctest`, `t.Context()`, `b.Loop()`, `os.Root`.
